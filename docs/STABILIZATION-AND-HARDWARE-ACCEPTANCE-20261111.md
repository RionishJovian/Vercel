# Mega-Magic stabilization: review gates and physical acceptance (2026-11-11)

**Status:** Implementation/CI evidence is separate from production acceptance. This is a checklist, **not proof that the tests have run**. Baseline reviewed: `main` at `e014fb3dc3c09d429dd356caae67143001ed4ec6`.

## Ordered stabilization
1. **Readiness, request-log redaction and release provenance:** draft PR #191, source tests passed on its previous head; recheck CI after any rebase. Before release, prove healthy `/ready` returns 200, a controlled missing DB/Redis/NATS dependency returns 503, public JSON contains no raw errors, and `/api/v1/version.commit` equals the running binary/image revision. Do not force a dependency failure on the customer-facing VPS merely to test.
2. **Client IP and rate limits:** issue #192, now draft PR #197. Read-only VPS inspection confirmed host Caddy -> web Caddy -> Go API and both diagnostic sources appearing as the web peer; source fixes and regression tests are prepared. **Release acceptance remains blocked** on stable exact proxy peers and the full production-shaped forwarding chain; test two independent client addresses, shared NAT, header spoofing and 50+ independent hotspot customer requests in a disposable production-shaped environment. Do not trust the whole Docker CIDR, arbitrary `X-Forwarded-For`, or a browser-supplied device identifier as security identity.
3. **Production integration encryption and webhook response redaction:** draft PR #193. Verify key is present without revealing its value; empty/invalid key must fail closed in a disposable production-shaped startup. Ensure list/create/update omit secret while notifier signatures remain valid. A failed CI test does not certify readiness.
4. **Internet Access Voucher issuance:** draft PR #194. The legacy `POST /api/v1/vouchers` must reject reserved `guest-internet` before DB writes. The real `POST /api/v1/guest-vouchers` batch path must retain router provisioning, readback, stable retry and accounting. Preserve previously issued 8-letter HotSpot vouchers and separate VIP codes.
5. **Deployment instructions:** draft PR #195. `main` pushes automatically deploy to VPS; DB migrations are not automatically rolled back. Operator must prove running image and commit, backed-up DB and rollback evidence before accepting a release.
6. **Real-device acceptance:** not completed; gates below need an authorized router and maintenance window.
7. **Developer workflow cleanup:** the repo root `dev` now targets current `app/` React UI; root `preview` targets the production-style `vercel-public/` build. Production media page and asset references gain static validation. CI cleanup is limited to removing an app build already performed by the production root build; distinct security, migration, backup, app and frontend checks remain.

## Physical-router acceptance checklist — NOT RUN in this audit
**Prerequisites:** select and identify one owned MikroTik gateway (model, RouterOS version, verified management identity, actual site), capture approved maintenance window, observe its own backup capability and a verified accessible rollback, record expected LAN/HotSpot topology and a non-revenue test voucher. Never factory-reset the owner's existing router or alter other customers. Capture only redacted evidence; no voucher codes, keys, passwords, receipts or full IP addresses in reports.

- **A. Router/Hub connection:** observe fresh WireGuard handshake and authenticated RouterOS identity-bound read. Unknown/offline/stale statuses must not be labelled connected. Check recovery after Hub interruption without overwriting unrelated configuration.
- **B. Initial HotSpot setup and portal:** on a test network, inspect planned bridge/port/SSID/DHCP/DNS changes; validate backup and owner approval before applying. RouterBOARD itself must serve the expected branded captive login, including through a bridged third-party AP where applicable.
- **C. Internet Access Voucher issuance:** owner issues one small batch in MikroMagic; verify each generated code exists as the intended RouterOS HotSpot username/password before marking the batch ready. Retried/unknown batches must not mint replacement codes or print unverified ones. Never publish example codes to evidence.
- **D. First use and continuity:** with mobile data disabled, customer enters a code on the router-served captive portal; verify actual HTTPS internet access, router-stamped first-use timestamp/MAC, unchanged expiry after disconnect/reconnect, usage accounting, single-device limit, hard local expiry and preservation through a controlled cloud/Hub outage.
- **E. Client and device controls:** test Kick, Ban, Unban and retained limitations, a real browsing client's block/unblock, backup creation/readback and safe change rollback; do not infer enforcement merely from command success. Record the previously observed bridge-name mismatch and failed backup capture until retested.
- **F. Mixed APs / SSID policy (N19):** one supported MikroTik radio and one supported third-party AP only in an explicitly authorized test scope; show observed/current SSID, precise preview, owner confirmation, per-device apply/readback, unsupported and offline states, and guest captive portal continuity. Current source implements only read-only SSID previews; **no end-to-end universal vendor rollout can be accepted**.
- **G. Capacity/rate limiting:** with a production-shaped proxy and controlled load (not the live paying hotspot), show 50 or more distinct simultaneous customer sessions behind one NAT can open/login without exhausting an unrelated customer's allocation. Verify missing/spoofed `X-Forwarded-For` cannot evade authentication abuse limits.
- **H. Payments and history:** verify monetary record transitions with dummy data, explicit owner approval, idempotency, tenant separation and recorded vs bank-settled distinction. No real payment or customer-data mutation.

For every item use **PASS / FAIL / NOT RUN / BLOCKED**, exact software SHA, deployed image digest if applicable, RouterOS and AP model/firmware, timestamp, redacted positive and negative evidence, rollback result, and next required action. A simulated RouterOS test, a passing unit test, preview screenshot and a successful VPS deploy never by themselves imply physical acceptance.

## Local developer commands
- `npm --prefix app ci` then `npm run dev` starts the **current React console**, available under `/v2/`. Its dev proxy preserves the browser Host and expects the separately started Go API at `http://127.0.0.1:8080` with a safe local database/config. It does **not** start production containers or RouterOS.
- `npm run build` generates `vercel-public/`; `npm run preview` previews that static build. The dedicated preview config forwards `/api` to the separately started local Go API on `127.0.0.1:8080` while preserving the browser Host; API-dependent flows still require that safe backend. It is not a signed-in or physical-router acceptance test.
- `npm run test:api` runs the current Go API suite; select an explicitly disposable `MM_TEST_DB_URL` for database coverage. `test:api:legacy` retains the historical Python command.
- `npm run dev:sites` and `npm run preview:sites` explicitly select the historical Sites/Vite prototype, not the currently deployed console. Existing historical code is preserved for forensic and rollback context rather than deleted prematurely.
- An actual VPS release continues to come only from the protected GitHub `main` release workflow after separate human review.
