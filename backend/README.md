# Account/payment backend — increment 2

FastAPI + SQLAlchemy, PostgreSQL via psycopg. Separate `/v1` API while existing preview retains `/api` demo storage. This does not silently migrate/overwrite demo orders. There is no role-selector or demo-login route in this service.

Create a virtual environment and install requirements.txt. Set DATABASE_URL to a PostgreSQL connection URL using the `postgresql+psycopg://` scheme. Keep credentials in deployment secrets.

```
alembic upgrade head
python -m backend.provision --username YOUR_USERNAME --role platform
uvicorn backend.app:create_app --factory --host 127.0.0.1 --port 8788
```

Provision SME/guest with --tenant-name. Passwords are entered privately at the terminal and Argon2-hashed. Use TLS reverse proxy for remote access. Authentication returns a one-hour opaque bearer token; only its SHA-256 digest is stored. Logout revokes it; user deactivation denies existing sessions. Failed login buckets are DB-persisted per username and direct peer address. Proxy/rate-limit configuration and multi-process contention tests are pending deployment work.

API docs at /docs. Role and tenant come from account records, not request-supplied claims. Platform accounts list tenants but do not automatically gain guest-order review permission. A scoped support delegation flow is still required.

Order creates use request_key for retry safety and snapshot package policy/price. Review transitions use conditional updates, a unique order entitlement and transactionally recorded outbox event. Approval queues fulfillment as pending_adapter; it never claims actual router access has been activated. Refund endpoint only records manual refund and revocation, it does not send money.

Migration 001 contains explicit frozen table operations. Future schema changes require a new migration; never change an applied migration.

Current tests run SQLAlchemy on isolated SQLite. PostgreSQL SQL compilation is checked; PostgreSQL runtime and concurrent transaction tests require a running PostgreSQL instance. No claim of production readiness.

Browser sign-in and account package/payment/revenue/audit workflows are connected. Remaining integration: guest onboarding, complete policy/API parity, media gateway and real router accounting. Guest orders now support protected image receipts as described under migration 011 below. Voucher counter-sale image attachments remain pending.

Portal revision migration 002 adds portal_settings and nullable order payment_context. SME-only draft and publish endpoints use revision checks; guest-facing projection excludes network fields. Publication requires payment instructions when purchases are enabled. New orders validate published revision and method, then store immutable recipient/instruction snapshots. `/v1/portal/public` currently requires an existing guest account; pre-login account resolution and site routing remain pending.

Migration 003 adds vouchers and optional voucher origins to entitlements, with an exactly-one order/voucher source constraint. Issuance uses request keys and snapshots policy. Codes contain 128 random bits and are stored only as digests, with masked hints for owner inventory. Full code recovery is intentionally unavailable. Atomic redemption grants one pass; retries by that guest return it. Revocation updates any stored pass in the same transaction. These actions never create payment orders or revenue. Voucher downgrade requires an online empty-voucher check and refuses to discard existing records.

Migration 004 adds voucher_sales. Exactly one counter collection is allowed per voucher. Required explicit receipt confirmation, price match and role/tenant checks precede recording. Refund confirmation records history and revokes voucher/pass atomically; no funds are moved. Both sale/refund retries preserve existing records. Revenue includes voucher sales separately from guest orders.

Migration 005 adds sites, router_devices and site_portals, plus nullable site references on orders/vouchers/entitlements. APIs validate tenant/site access before registration or portal selection. Reported router state cannot be supplied by a client. Guests see published site names and public content, not private router/config fields. Legacy portal APIs still work. Site history cannot be silently discarded via downgrade. WireGuard, capabilities and per-site accounting filters remain pending.

Migration 006 adds immutable platform-owned MagicHub records, composite business assignments and per-router plans. Platform POST /v1/hubs and /v1/hubs/{id}/assignments; SME GET /v1/hubs only lists assigned hubs. Platform GET /v1/hub-assignments is restricted. SME POST /v1/routers/{id}/plan requires its own router, assigned hub and canonical public key. GET /v1/router-plans is scoped to SME or platform fleet. POST /v1/router-plans/{id}/review requires SME confirmation and records acknowledgement once. Guests have no access.

Allocation updates hub.next_host atomically with RETURNING in the same transaction as plan/audit creation. Unique router/public-key/hub-address constraints reject races; identical retries return the stored immutable plan. Pools are RFC1918 aligned /24 networks, reserve .1 and network/broadcast, and cannot duplicate existing pools. Known portal subnet conflicts block creation; full live subnet checks and revalidation before any application are pending. No private keys, executable commands, telemetry setters, worker dispatch or false online state are implemented. Registry hub_id identifies planned association, not a verified connection. Key rotation, hub migration/removal and assignment revocation need explicit lifecycle workflows. Downgrade refuses to discard hub records.

Migration 007 adds append-only-through-API financial_events. Approval and refund transactions write one event per source/kind; uniqueness prevents duplicate accounting. Financial snapshots preserve package/method/reference/source/site and recording timestamp independently of later source edits. Source identifiers are historical references; there is no destructive ledger editing endpoint. Audit-based legacy migration marks timestamps as migrated_audit, stored voucher times as migrated_record, and missing order times as legacy_submission_estimate. Unknown legacy refund actors remain null.

SME GET /v1/revenue and /v1/revenue/ledger accept optional start/end ISO dates (both or neither), timezone (default Asia/Yangon), and site_id (owned site, unassigned, or omitted/all). Inclusive dates become local-midnight UTC boundaries; ranges are limited to 366 days. Financial period filters use event recording dates. Pending queue uses submission dates/current pending status. Negative-period net is valid. Ledger limit defaults to 100, max 10000; offset max 1000000; has_more uses an extra fetched row rather than a potentially concurrent count. All access is tenant-scoped, including site validation. Runtime PostgreSQL, scalable aggregation/index tuning and external cash reconciliation remain pending.

Migration 008 adds theme_settings. GET /v1/appearance and POST /draft, /publish, /restore are platform-only and require expected_revision on writes. Draft accepts exactly two five-token six-digit hex palettes and unique role scopes; arbitrary CSS and tenant override fields are rejected. GET /v1/appearance/effective uses the authenticated role. Public /v1/appearance/public exposes only effective platform/sign-in colors. Effective responses use no-store. Excluded roles get defaults; there is no tenant override API.

Conditional revision updates and transactional audit protect publication/restore races. Publish rejects low contrast and a draft identical to current publication. Restore swaps current/previous palettes and scopes, replacing the draft. Color-mix calculations match CSS sRGB blends for 20 listed text pairs; threshold is 4.5:1. Border/focus/hover/disabled and exhaustive component accessibility remain unverified. Live propagation uses refresh/next sign-in, not WebSocket push.

Migration 009 adds tenant-scoped media_titles. SME POST /v1/media/titles creates draft metadata; POST /{id} edits with expected_revision and returns the title to draft. POST /{id}/state accepts publish/unpublish/archive/restore with revision checks; restore requires an archived title. GET /v1/media/titles lists all own metadata for SME, and published/non-archived own-business titles for guest. Platform has no implicit catalogue scope.

Media PackageIn accepts library/title/hybrid; elapsed viewing windows only. Hybrid uses hours for library and title_hours (default 48) for the chosen title. Title/hybrid creation validates owned active catalogue ID and writes title_snapshot server-side. Guest offers/new orders/approvals/voucher issuance require publication; media-only library offers require a published title. Conditional title-row updates claim a lock before relevant new sales/approvals/issuance to serialize against withdrawal. Existing exact retries retain history. Previously issued valid voucher redemption is not blocked by later catalogue withdrawal.

Entitlement media_policy describes library/title windows and the immutable title snapshot, with playback/activation explicitly disconnected. Combined uses media_hours independently of internet policy. No stream authorization, elapsed-time enforcement, replay count or file/segment access endpoint is implemented. Legacy unresolved title IDs retain pass history and cannot produce new title sales without catalogue mapping. Shared business catalogue has no per-site file-server mapping yet.


Migration 011 adds receipt_images (private database binary storage) and orders.receipt_revision. The purchasing guest POSTs raw JPEG/PNG bytes to /v1/orders/{id}/receipts with a unique X-Upload-Key; the UI attaches images under My access after creating an order. Up to three images per order, 5 MiB input, 8 million decoded pixels and 8 MiB normalized storage per image. Pillow decodes and re-encodes a lossless PNG without input metadata or appended data; EXIF orientation is applied. Original files are not retained, but the input SHA-256 is recorded for retry comparison. HEIC, PDF and animated images are unsupported. See [Pillow image documentation](https://pillow.readthedocs.io/en/stable/reference/Image.html) for decoding and pixel-limit APIs.

A conditional order-row update serializes attachment counts, retries and review transitions. A repeated upload key with identical bytes returns the stored receipt even after decision; another image with that key conflicts. New uploads require pending/needs_evidence. Upload increments receipt_revision without approving or resubmitting the payment. Review requires expected_receipt_revision when any receipt exists and compares it atomically with pending status; legacy no-receipt API requests may omit the field. The UI always includes the current revision.

GET /v1/orders/{id}/receipts lists metadata and GET /{receipt_id} returns authenticated image/png with no-store, nosniff and sandbox CSP. Both require same-business SME or exact purchasing guest; platform and foreign guest/tenant reads are denied. No public image URL, original filename or token-in-URL is exposed. Viewing is audited. The frontend fetches with the in-memory bearer, displays a temporary object URL and revokes it on replacement/close/unmount. Images remain available after review/refund; no deletion endpoint is provided.

Middleware bounds streamed request bytes before materializing the body: receipt uploads up to 5 MiB; other requests retain 64 KB limit. This is not deployment rate limiting. Database/object-storage sizing, retention policies, encrypted deployment backups, scan/abuse controls, concurrent PostgreSQL verification and authenticated/mobile browser testing remain pending. Receipt upload never independently proves receipt of funds or grants internet/media access. Downgrade refuses to discard stored receipt images.


Migration 012 adds owner-bound review_credentials and external_review_actions. SME Integrations creates read-only or read+decision tokens, shown once and stored only as hashes; expiration 1–90 days, revocation reason and owner-deactivation checks. External review routes use a separate bearer authentication path and cannot use account sessions or gain arbitrary account API access. Tokens delegate authority to the creating SME account, with a configured reviewer identity claim that the trusted platform adapter must verify independently. No Telegram/Discord bot is connected.

The review API returns full scoped order context and private receipt access, requires the displayed order context hash and receipt version, deduplicates exact callbacks by credential/request key, and shares the dashboard's atomic payment transaction. Service/provider/identity snapshots and results record how the action was requested. Owner user ID remains the authorizing account; external history distinguishes the service credential and reviewer claim. Read-only credentials cannot decide, and no delegated refund API exists. See [REVIEW_API.md](REVIEW_API.md) for the complete contract, sample requests and remaining adapter/notification/deployment acceptance work.


Migration 013 adds order event_revision, nullable legacy outbox snapshot/time/revision, explicit future-event subscription on review credentials and per-credential event_deliveries. The old unique (order,event-name) constraint becomes unique (order,revision) so repeated evidence cycles work. Payment creation, resubmission, decisions and refund now emit transactional immutable snapshots and fan out to active subscribers. Legacy records remain unchanged and are not auto-replayed. Pull claims lease events, hashed tokens fence stale workers, completion deduplication/backoff/five-attempt failure handling and owner manual retry preserve payment history. There is no outgoing network dispatcher or bot connection. See REVIEW_API.md for the pull protocol and at-least-once semantics. Owner integration UI shows queue status; queue reassignment, lease renewal and full per-attempt error history remain pending.


Migration 014 adds users.must_change_password and temporary_password_expires, business_provisioning retry records and password_reset_records. Existing accounts keep their hashes, roles and access (password-change flag defaults false). Platform GET/POST /v1/platform/businesses lists business owners and creates a tenant plus its first SME owner, with a private random 24-hour temporary password returned once. Creation retries return metadata without recovering the secret; changed key reuse/global username conflicts fail. Portal starts as an unpublished draft with direct purchase and voucher login disabled. No subscription or live router is created.

First-login accounts may only read /v1/me, change their password or sign out; all authenticated business endpoints are blocked until completion. Expired temporary passwords require operator reset. /v1/auth/password verifies the current password, requires a different nonblank password of at least 12 characters, throttles wrong-password attempts, compares the stored hash atomically, invalidates every existing browser session and returns a fresh one-hour token for the current browser. Ordinary password changes preserve independently delegated service credentials; forced platform recovery revokes them. Account role/tenant are never client supplied.

Platform POST /v1/platform/businesses/{id}/owners/{owner_id}/reset-password requires a reason and authority confirmation. It can only target a same-business SME owner, never a platform/guest account. It preserves the account's active state, resets the account login and password-change failure buckets, stores the reason, ends browser sessions and revokes owner-bound review credentials. It returns another one-time 24-hour password. GET /v1/platform/password-resets is platform-only and returns the latest 200 reset reasons/actors without secrets. A disabled account remains disabled. Password change has its own separate 15-minute wrong-password bucket; platform recovery clears both account-specific buckets. The global direct-peer login bucket retains its normal window.

The platform Businesses UI creates accounts, shows one-time handoff details, lists owner readiness and reset history, and supports reset. All roles have an Account password-change page; first-login users see only the required password form. No credential message is sent. Platform bootstrap remains the trusted CLI provisioning step. Subscription plans, owner/staff lifecycle, email recovery/MFA, guest signup/pre-login tenant resolution, contact onboarding and production bot/router connection remain pending. Downgrade refuses to discard new onboarding/reset or mandatory-password records.
